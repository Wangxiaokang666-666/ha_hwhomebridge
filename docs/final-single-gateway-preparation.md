## 配置如何合并

同一个原配置条目、父网关 SN 和账号配对资料下，保留 32 个旧子设备的 SN、PID 和实际服务绑定，再追加书房设备的 7 张补充卡片。原主灯 `002` 继续承担开关、亮度和色温；不再创建一张替代主灯。

公共组合规则新增两个声明：

- 主卡声明 `primary_role: "main"`。保留前先确认原卡的全部控制确实指向该角色，否则拒绝整份计划。
- 补充卡声明 `share_when_primary_preserved: ["switch"]`，保留模板的主灯服务，但显式共享原主卡的同一开关。仅允许同实体的普通二值开关；值映射、额外参数、`on_command` 或其他副作用均拒绝。其余重复控制继续拒绝。

这些规则只改变 HA 控制组合，不能改写华为 profile 的特性定义。`20UC`、`2151` 的原 profile 使用 `serviceType=switch`；已实测的云端 `switch1` 等别名继续由单独的 `cloud_service_type` 声明，不把云端兼容别名当作原 profile 类型。

风扇仍按六档加自然风接入；正反转使用已修复的厂家映射。原生定时由设备的 enable/duration/remaining 三个角色完成；不会新增 Python 软件计时器，也不调整米家面板的双向同步自动化。

## 离线准备和验真入口

```sh
python3 tools/ha_gateway_prepare.py \
  --cold /secure/verified-cold-export \
  --frozen /secure/verified-frozen-bindings \
  --profiles /secure/reviewed-profiles \
  --endpoint /secure/cloud-endpoint.private.json \
  --instances /secure/study-roles.private.json \
  --snapshot /secure/fresh-snapshot.private.json \
  --native /secure/build-ha-static-x86_64 \
  --ca /secure/huawei-cbg-root-ca.pem \
  --output /secure/new-offline-preparation
```

输入须来自同一原 HA 身份及未变化的注册表。工具核对冷备、常驻绑定、实体归属、设备型号、已注册 HA 控制服务、产品指纹、原 profile 和当前原生源码摘要。原生定时也核对 switch 和 number 服务。任何检查失败都不发布半套目录；输出必须在仓库和所有输入之外，目录 `0700`、文件 `0600`。

输出在 `config/.storage/hwhomebridge/gateways/current/` 下，包含冻结绑定、角色配置、公开映射、私有 profile、原配对 KV、旧引擎回退配置及两份 x86 静态程序。目标 CA 路径以 `/config` 为根；保持原接口/MAC、云端连接参数和全部旧云 ID。配对 PIN 已失效，不开放新配对。

`deployment.json` 必须保留 `offline_preparation: true`：`GatewayDeployment.verify_engine()` 在任何网络或读取器调用之前拒绝启动两种引擎。外层私有收据记录全部文件摘要、版本、生成时间及原冷备时间。这份目录是接管准备材料，不是当前可以启用的生产配置。

独立 Linux 中以 `--network none --read-only --cap-drop ALL` 和只读源挂载运行：

```sh
PYTHONPATH=/code python3 -B /code/tools/ha_gateway_verify.py --bundle /bundle
```

`/bundle` 挂载准备目录，`/config` 挂载其 config 子目录，`/code` 挂载公共组件与 tools；仅 `/tmp` 提供临时内存文件系统。验证器要求网络 namespace 只有 `lo`。它校验全部文件摘要、完整受管配置和新增 SN 的确定性，确认两种引擎均被阻止，再运行真正的 C 身份读取器。

上游 KV 读取以 `rb+` 打开文件；因此读取器使用 `/tmp` 内可写的临时 KV 副本，源目录一直只读。探针读到的根身份及五个账号字段须与冷备逐项一致，临时副本和原文件都不得变化。不会运行 SDK 主任务。32 个旧子设备加 7 张补充卡片已通过这条实际 x86 读取路径；`production_adoption_ready` 仍为 `false`。

## 独立 x86 HA 的实际回退

本轮运行实际 amd64 HA Core 2026.10.1、固定版本旧闭源库和真实 OpenHarmony C。宿主是 ARM Linux，amd64 用户态通过 qemu-user 执行；不是原生 x86 硬件或完整 x86 内核验收。镜像从原机已有的不可变镜像只读导出，未导出运行配置；导出前后容器 ID、镜像、配置、启动时间及挂载集合一致。

实验只加载已配对的虚构身份和 `oh_single_` 虚拟实体；不加载生产身份。一个父身份下有 8 个旧品类和 7 张补充卡片，任一时刻只有一个原生所有者。

`gateway_availability_ha_test.py exercise` 验证一张旧灯离线时，真实旧 SDK 和 OpenHarmony 均可上线；其他卡片可控，离线和同值恢复均得到云端确认。杀死 OpenHarmony 进程后真实旧 SDK 自动接管，原条目和配对文件保持。

新增 `failback` 阶段故意保留失败记录后结束 HA；下一次新 HA Python 进程必须继续选用旧 SDK，不能在重启时悄悄重试失败引擎。App 观察夹具 `gateway_app_acceptance.py --expected-boot legacy` 对同条目、单所有者和原配对字节作断言。

App 验收通过真实智慧生活 → 云端 → C 回调 → 公共 HA 路由，再读回虚拟 HA 状态。私有文件通道只允许查询、观测标记、显式后端切换、重置虚拟状态和停止，不提供模拟控制写入；每次操作先在 App 设备信息中精确核对实验子 SN。原始日志及带账号信息的 UI 截图不提交。最终实测范围见[脱敏记录](../experiments/openharmony_bridge/evidence/final-single-gateway-validation.json)。

定时页的实际流程是选择设备，再选择时长；确认时长后直接启动选中设备的原生定时，没有额外的“开始”按钮。取消后页面清空选择和时长，需要重新选择。实验已从 App 同时启用灯和风扇的 1 分钟定时，逐项读回两个 enable、duration、remaining；再从 App 取消，两个 enable 均关闭、remaining 均为零，其他虚拟实体不变。此处 1 分钟是夹具值，不是实物计时精度结论。

现成厂商模板的 UI 仍有多余入口：`28BF` 显示八档，但本型号只声明六档，七、八档会被映射层拒绝；未支持的摇头、睡眠风、背光等不能作为新增能力宣传。选择一至六档可退出自然风，模板的“正常风”独立按钮没有额外映射。`2NAL` 保留本组合声明的六个服务，其原 profile 共十七个服务，并未全部接入；该页面的亮度、色温及渐变等未映射入口和默认显示不能当作主灯实际状态。主灯亮度、色温继续使用原 `002` 卡；组合模板里的主灯开关使用上述明确共享规则。定时夹具模拟设备保存时长、启用与剩余值，证明的是 App 到原生定时实体的路由和重启读回，不替代真实风扇走完定时的硬件验收。

模拟环境中有一次“空场景”写入到达 HA，但 C 层未确认，不能计为成功。保留首个失败后，从 App 关闭并重新开启，两次均收到 C 确认且 HA 读回一致，分别约 3.2 秒、4.0 秒。尚未证明首次未确认的具体根因，也不能据此声称生产链路零超时；原生 x86 和真实设备的持续稳定性仍需后续验收。

公开回归入口：

```sh
python3 -m unittest discover -s tests
python3 -m unittest discover -s tools -p 'test_*.py'
python3 custom_components/hwhomebridge/validate_config.py
```

本轮公共回归 80 项、工具回归 121 项和配置校验通过。保留式安装包生成、离线安装及还原继续使用 [安装说明](openharmony-installation.md) 中的工具，不能直接覆盖整个组件目录而丢掉原 SDK 配置。

`b6 → b8 → b6 → b8` 已在独立原生 ARM Linux 与实际 ARM HA 镜像中完成文件安装演练，逐项核对 56 个包文件；条目字节、配对目录、原配置、库和 profile 保持不变，安装器没有启动 HA。amd64 的云端/App 验收使用上文独立的 qemu-user 环境，两者分开记录，不能把 ARM 安装预检当作原生 x86 主机验收。

## 生产交接前仍需完成

本轮输入使用既有冷备并刷新只读实体和实际绑定观察。未来正式维护窗口必须重新取得一致冷备、复核当前原生库/实体/端点并重新生成目录；不能直接把本轮旧冷备当作实时回滚点。

完成明确的生产切换任务后，才解除离线阻止、按维护方案停旧所有者并交给同一身份的新所有者。先验证全部旧卡、书房组合能力、App 实际读写和重启，再保留真实旧 SDK 回退。旧 SDK 回退只覆盖原 001–008，新增风扇卡不能宣称在旧 SDK 下可用。

当前 App 使用实验网关的云端通道；原机局域网端口、LAN 控制与 39 个子设备的实际启动时长尚未验收，必须纳入正式接管窗口。不能把这轮虚拟设备云端验收当作原机 LAN 接管或真实风扇计时验收。
